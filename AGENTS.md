# AGENTS.md

This file provides guidance to Codex (Codex.ai/code) when working with code in this repository.

## Commands

```bash
make run        # go run main.go (starts root CLI)
make api        # go run main.go api (starts HTTP server)
make build      # build binary to bin/server
make generate   # run sqlc generate (regenerates internal/repository/dbgen/)
```

```bash
make test              # go test ./... (integration tests skip without TEST_DB_DSN)
make test-integration  # starts throwaway PG+Redis, migrates, runs the real suite
make test-integration-down  # remove those containers
```

Three test layers, cheapest first:

- `arch_test.go` — the layering rules above, by parsing imports. No dependencies.
- `internal/domain/rules_test.go` — the infrastructure-free business rules, boundary
  values included. Runs in ~0.1s without docker.
- `internal/apps/api_test.go` — the real HTTP stack against a real PostgreSQL and
  Redis, deliberately **not** mocks: the logic worth guarding lives in SQL and cache
  invalidation (timezone-resolved dates, ILIKE escaping, transaction rollback), and a
  mock would skip exactly that. Skips when `TEST_DB_DSN` is unset, so plain
  `go test ./...` still runs the first two layers without docker; CI
  (`.github/workflows/test.yml`) always sets it.

Run a single test: `go test ./internal/apps/ -run TestBatchIsAtomic`
Lint: `golangci-lint run` (if installed)

## Architecture

This is a Go REST API using [Fiber v3](https://github.com/gofiber/fiber) for a personal finance/bill tracking app.

### Request Lifecycle

```
main.go → cmd/ (Cobra) → internal/apps/app.go → StartAPIServer()
  ↓
Fiber app + Middleware stack (logger, CORS, error handler, panic recovery)
  ↓
internal/apps/router.go → handlers/ → services/ → repository/dbgen/ (sqlc) → PostgreSQL
```

### Layer Responsibilities

Dependencies point inwards. `internal/domain` is the centre and imports no
infrastructure at all; everything else may depend on it.

| Layer | Path | Role |
|-------|------|------|
| Domain | `internal/domain/rules.go` | Business rules needing **no** database, cache or HTTP. Unit-tested in ms. |
| Domain | `internal/domain/models.go` | Every type crossing a layer boundary (`Bill`, `APIKey`, `User`, `CategoryNode`, stats outputs) |
| CSV | `internal/csvimport/` | Bytes → transaction records. Also infrastructure-free: no file or network access. |
| Config | `config/config.go` | Env var parsing via `caarlos0/env` |
| Database | `internal/database/` | pgx connection pool + Redis client |
| Repository | `internal/repository/dbgen/` | **Generated by sqlc — do not edit manually** |
| Mapping | `internal/services/mapping.go` | sqlc row → domain type; the only place that knows both shapes |
| Services | `internal/services/` | Orchestration: reads/writes + cache + transactions; aggregated in `service.go` |
| Handlers | `internal/handlers/` | Fiber context parsing; aggregated in `handler.go` |
| Middleware | `middleware/` | JWT auth, error formatting, context helpers |
| Utilities | `pkg/` | `logx/` (zerolog wrapper), `errorx/` (typed errors), `utils/` (JWT gen/parse) |

### Layering rules

**These are enforced by `arch_test.go`, not just documented** — it parses every
non-test file's imports and fails the build on a violation. Add a rule there when
you add a boundary.

1. **`internal/domain` imports no infrastructure.** No pgx, no redis, no fiber, no
   other package of this module except `pkg/`. That is what lets its rules be
   tested without docker. Rules needing a read (does this category belong to the
   user?) stay in the service layer; only the decision that follows the read is
   modelled in domain, e.g. `MatchSecondLevelCategory`.
2. **No `dbgen` type appears in a service's exported signature.** Services return
   the types in `internal/domain/models.go`, built by the `*FromRow` converters in
   `internal/services/mapping.go`. This keeps a schema change inside the service
   layer, and keeps secrets out of upper layers — `dbgen.ApiKey` carries `KeyHash`
   and `dbgen.User` carries `PasswordHash`; neither domain type does. Handlers must
   not import `dbgen` at all, and swagger annotations reference `domain.*`.
3. **Services must not import the transport layer** (handlers, middleware, fiber),
   and `cmd/` must not link the service layer — the CLI is an HTTP client, the one
   exception being `cmd/api.go` starting the server via `internal/apps`.
4. **Every bill write goes through `BillService.invalidateStatsFor`.** A write that
   skips it leaves `/api/stats` serving pre-write totals. Routing all four paths
   (create, batch, update, delete) through one method keeps the rule in one place;
   `TestStatsCacheInvalidatedOnWrite` is what catches a path that forgets. This one
   is *not* compile-enforced — the test is the guard.
5. **Services are constructed from `services.Deps`, not positional parameters**, so
   adding an infrastructure dependency does not touch every constructor and call
   site. `Deps.Pool` is only needed by services running multi-statement
   transactions (auth, bill).

`internal/services/bill*.go` is split by responsibility: `bill.go` (write paths),
`bill_read.go` (queries), `bill_prepare.go` (payload preparation).

`apps.NewFiberApp(cfg, svc)` assembles the HTTP stack without starting it, which is
what lets the tests drive the real router via `app.Test` instead of binding a port.

The layering stops short of a full onion: there is no repository interface and no
`UnitOfWork`. That was a deliberate call — the rules that need no data are only ~19
simple checks, while `Register` and `BatchCreateBills` both need multi-statement
transactions that an interface-per-repository would force through an awkward
abstraction. Revisit if the domain grows real invariants.

### Database

- PostgreSQL via pgx/v5; Redis via go-redis/v9
- Schema: `sqlc/schema.sql` | Queries: `sqlc/queries.sql`
- After modifying SQL files, run `make generate` to update `internal/repository/dbgen/`
- `make generate` needs sqlc **v1.30.0** (`go install github.com/sqlc-dev/sqlc/cmd/sqlc@v1.30.0`);
  other versions only differ in the generated version comment, but that shows up as diff noise
- sqlc overrides: `pgtype.UUID` → `uuid.UUID`, numeric → `decimal.Decimal`, timestamps → `time.Time`

### Auth

- JWT (HS256, 72h expiry) stored as Bearer token
- `middleware/auth.go` validates token and stores `user_id` + `email` in Fiber `Locals`
- Passwords hashed with bcrypt

### Error Handling

- Use `pkg/errorx` to create errors with HTTP status codes: `errorx.New(http.StatusBadRequest, "message")`
- Global error handler in `middleware/error.go` returns `{"success": false, "code": N, "message": "..."}`
- Logging via `pkg/logx`: `logx.WithError(err).WithField("k", "v").Error("msg")`

### Routes

`/api/bills` and `/api/transactions` are two path aliases for the same handlers.

```
GET  /api/ping
POST /api/auth/check-email        (rate limited: 10/min per IP)
POST /api/auth/register           (rate limited)
POST /api/auth/login              (rate limited)
POST /api/auth/refresh            (rate limited)
POST /api/auth/logout
GET  /api/auth/me                 (JWT only)

POST   /api/api-keys/             (JWT only)
GET    /api/api-keys/             (JWT only)
POST   /api/api-keys/:id/revoke   (JWT only)
DELETE /api/api-keys/:id          (JWT only)

GET  /api/categories/             scope categories:read
POST /api/categories/             scope categories:write

GET    /api/transactions/         scope transactions:read
GET    /api/transactions/:id      scope transactions:read
POST   /api/transactions/         scope transactions:write
POST   /api/transactions/batch    scope transactions:write
PUT    /api/transactions/:id      scope transactions:update
DELETE /api/transactions/:id      scope transactions:delete

GET  /api/stats/monthly           scope stats:read
GET  /api/stats/daily             scope stats:read
GET  /api/stats/category          scope stats:read
GET  /api/stats/home              scope stats:read (alias of monthly)
```

Scoped routes accept either a JWT `Authorization: Bearer` header or an
`X-API-Key` header whose key carries the listed scope.

### CLI client

The same binary is both the server (`sumi api`) and an HTTP client for it. Client
commands live in `cmd/bill.go`, `cmd/category.go`, `cmd/stats.go`, sharing
`cmd/client.go`; the agent-facing usage guide is `skills/sumi/SKILL.md`.

An agent container gets the client in one of two ways:

- `skills/sumi/scripts/install-cli.sh` downloads the release asset for its
  OS/arch into `/usr/local/bin` (falling back to `~/.local/bin` when not root).
  Re-running it is a no-op. `SUMI_CLI_URL` overrides the source for a private
  mirror, `SUMI_CLI_DIR` the destination. Those assets come from
  `.github/workflows/release-cli.yml`, which cross-compiles static binaries on
  tag push and attaches them to the release — **until that workflow has run for a
  tag, the download 404s** and the script prints the docker fallback below.
- Copying `/app/server` out of the published image (`ghcr.io/solren7/sumi`),
  which is the same binary.

```bash
sumi auth login --email me@example.com          # prompts for the password (no echo)
printf '%s' "$PW" | sumi auth login --email me@example.com --password-stdin
sumi auth key create --name my-agent   # stores the key locally; no env vars needed after this
sumi auth status                       # which credential is in effect, and is it valid
sumi bill add --amount 25.50 --category 吃 --note 午饭
sumi bill add-batch --items '[{"amount":"12","category":"吃"}]'
sumi bill list --keyword 午饭 --from 2026-08-01 --to 2026-09-01
sumi bill update <id> --amount 31.00     # read-modify-write, see below
sumi bill del <id>
sumi bill import --file bill.csv --map date=交易时间,amount=金额 --dry-run
sumi category list | sumi category add --name 宠物 --parent 非必要
sumi stats monthly | daily | category
```

### CSV import

`sumi bill import` parses the CSV **client-side** and posts it as one atomic batch.
The split of work is deliberate: an agent reads only the header to work out
`--map` / `--category-map` / `--skip-rows`, and the CLI converts every data row.
That keeps the agent away from the numbers (it cannot mistype an amount) and keeps
the import atomic (an agent looping over `add-batch` could leave it half applied).

- `internal/csvimport/` is pure conversion — bytes in, records out, no file or
  network access, so every format quirk is covered by fast unit tests. It handles
  GBK, a UTF-8 BOM, `¥`/thousands separators/parenthesised negatives, eight date
  layouts, Chinese type words, preamble rows, and reports the **original file's**
  row number for anything it rejects.
- It deliberately has **no per-platform presets**. Column layouts change and there
  is always one more format; the caller supplies a mapping instead.
- Zero-amount rows are dropped before the type is interpreted, because wallet
  exports pair `0.00` with a type like `不计收支` that is neither expense nor income.
- Strict by default: one unconvertible row aborts the file. `--skip-invalid`
  switches to collecting them.

`domain.MaxBatchSize` is 1000 so a whole file fits one transaction. `cmd/import.go`
duplicates that number rather than importing `internal/domain`, since `arch_test.go`
keeps the CLI off the server's packages; the server enforces the real limit anyway.

Batch inserts share one `billLookups` cache, so a 1000-row import reads the user
and the category tree once instead of once per row.

- Credentials resolve as **env > config file**. `SUMI_API_URL` (default
  `http://localhost:3000`) and `SUMI_API_KEY` override whatever `sumi auth` stored
  in `~/.config/sumi/config.json` (`SUMI_CONFIG` moves it, `XDG_CONFIG_HOME` is
  honoured). The file is written 0600 via a temp-file rename.
- `auth login`/`auth register` take the password from `--password-stdin` (scripts and
  agents), `--password` (visible in the process list), or an interactive prompt with
  echo disabled. The prompt is the default for a person because the shell tricks that
  keep a password out of history differ between bash and fish; it refuses to prompt
  when stdin is not a terminal, so a non-interactive caller errors instead of hanging.
  `register` asks twice, since a typo in an unechoed password would create an account
  nobody can log into.
- Data commands authenticate with `X-API-Key`; `sumi auth` uses a bearer token,
  because API keys cannot manage sessions or other keys. An expired access token is
  refreshed once automatically and the new pair written back to the config.
- `auth key create` defaults to every scope the skill needs, and prints the
  plaintext key (the API returns it only once) while also storing it.
- Only `auth key revoke` is exposed: the API's `DELETE /api/api-keys/:id` is an
  alias of revoke — the row survives with `status: revoked` — so offering a `del`
  command would imply a removal that never happens.
- Parent commands (`bill`, `auth`, `auth key`, …) reject an unknown subcommand with
  a non-zero exit instead of cobra's default help-and-exit-0, which a script would
  misread as success.
- Output contract: success prints exactly one JSON document to stdout; failure
  prints nothing to stdout, the server's message to stderr, and exits non-zero.
- `--type` accepts `expense`/`income` and maps onto the API's `1`/`2`.
- `bill update` GETs the row and resends every field, because the API's PUT is a
  full replace — sending one flag alone would blank the other columns.
- `bill list --category` takes a *name*; the client resolves it to an id because
  the API filters by `category_id` only.

### AI/agent-facing conventions

These exist so a non-interactive client can record a bill without a lookup round-trip:

- A bill may set `category_name` instead of `category_id`. Names resolve against
  **second-level categories only** (bills cannot reference first-level ones). An
  ambiguous name is rejected rather than guessed.
- `POST /api/categories` creates second-level categories only, and rejects a name
  that already exists at level 2 for that type — that uniqueness is what keeps
  `category_name` lookups unambiguous.
- Omitting `currency` falls back to `users.default_currency`.
- Omitting `occurred_at` records today **as seen from `users.timezone`**, not from
  the server's or client's local zone. This has to be resolved server-side: a
  UTC-based client would otherwise file an evening bill under the previous day.
- `GET /api/transactions?keyword=` does a case-insensitive substring match on
  `description`; `%` and `_` in the keyword are escaped and matched literally.
- `POST /api/transactions/batch` inserts all items in one transaction (max 1000,
  sized so a whole CSV file fits one transaction).
  A rejected item aborts the whole batch and the error names its index, e.g.
  `items[1]: Category "x" not found`.
